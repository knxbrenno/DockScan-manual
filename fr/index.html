Votre point de départ : le Painel

Une fois l’accès configuré, ouvrez l’interface. Le Painel (Tableau de bord) rassemble les constats les plus récents de chaque cible, les analyses récentes et les éléments qui demandent votre attention.

Vous ouvrez l’interface locale ?

Une fois DockScan installé, exécutez la commande ci-dessous et ouvrez l’adresse affichée dans le terminal. L’adresse locale par défaut est http://127.0.0.1:8443.

python -m dockscan ui

Comment utiliser ce manuel

Suivez les chapitres dans l’ordre ou utilisez le sommaire pour aller directement à votre tâche. Les instructions peuvent être suivies sans les images.

Les écrans proviennent du laboratoire de DockScan, avec des données de démonstration. Le guide commence une fois que vous avez accès à l’interface. Pour vous connecter, changer votre mot de passe et gérer les comptes de l’équipe, consultez Comptes et accès.

DockScan est en cours de développement : découvrez ce qui vient d’arriver et ce qui se prépare.

Ce que DockScan reconnaît

Les systèmes, langages, programmes, services et formats que DockScan sait lire, et ce qu’il recherche dans chacun. Ce qui ne figure pas dans cette liste n’est pas analysé. Les éléments en développement ne sont pas encore lus : ce sont les prochaines étapes de l’outil.

Systèmes d’exploitation

Les paquets du système sont lus sur les machines, dans les conteneurs et dans les images. Pour tous ces systèmes, DockScan signale aussi quand la version sort du support de sécurité.

  • Debian

    Distribution Linux communautaire, base d’une bonne partie des images officielles.

    Les paquets dpkg, y compris dans les images distroless, et les avis de Debian.

  • Ubuntu

    Distribution Linux de Canonical, courante sur les serveurs et dans le cloud.

    Les paquets dpkg et les avis d’Ubuntu propres à chaque version.

  • Alpine Linux

    Distribution minimale, base de nombreuses images de conteneurs.

    Les paquets apk, selon la version d’Alpine, vérifiés aussi dans la base de sécurité d’Alpine elle-même.

  • Rocky Linux

    Distribution compatible avec Red Hat Enterprise Linux.

    Les paquets RPM et les avis de Rocky Linux.

  • AlmaLinux

    Distribution compatible avec Red Hat Enterprise Linux.

    Les paquets RPM et les avis d’AlmaLinux.

  • Noyau Linux

    Le cœur du système d’exploitation.

    La version en cours d’exécution sur chaque machine, avec le total des CVE et celles qui comptent maintenant.

Pour ceux-ci, DockScan signale déjà la fin de support. La vérification de leurs paquets est en développement.

Langages de programmation

Les dépendances sont lues dans les fichiers du projet, dans les paquets installés sur les machines, dans les conteneurs et dans les images, et dans les programmes déjà compilés. Hors du gestionnaire signifie installé sans apt, apk ni dnf, comme dans les images officielles : la version est lue dans le fichier lui-même, sans rien exécuter.

  • Python

    Langage d’automatisation, de données et d’applications web.

    requirements.txt, poetry.lock, Pipfile.lock, uv.lock et les paquets installés. Également Python installé hors du gestionnaire.

  • Node.js

    JavaScript côté serveur, avec les paquets npm.

    package-lock.json, yarn.lock, pnpm-lock.yaml, bun.lock et node_modules. Également Node installé hors du gestionnaire.

  • Go

    Langage compilé, courant dans les outils d’infrastructure.

    go.mod, go.sum et les programmes compilés avec Go 1.13 ou plus récent, qui contiennent les modules et la version de Go.

  • Ruby

    Langage de Ruby on Rails, avec les paquets RubyGems.

    Gemfile.lock et les gems installées. Également Ruby installé hors du gestionnaire.

  • PHP

    Langage de sites et de systèmes web, avec les paquets Composer.

    composer.lock et les paquets installés. Également PHP installé hors du gestionnaire.

  • Rust

    Langage compilé axé sur la sécurité de la mémoire.

    Cargo.lock et les programmes compilés avec cargo-auditable, qui enregistrent les dépendances.

  • Java

    Langage de la JVM, avec les bibliothèques Maven.

    .jar, .war et .ear, d’après les données Maven ou leur empreinte dans Maven Central, y compris les bibliothèques contenues dans d’autres ; pom.xml et gradle.lockfile. Également Java installé hors du gestionnaire.

  • .NET

    Plateforme de Microsoft pour C# et F#, avec les paquets NuGet.

    Le fichier .deps.json des applications, le fichier packages.lock.json des projets et le runtime .NET installé.

  • Elixir

    Langage fonctionnel, avec les paquets Hex.

    Le fichier mix.lock des projets.

  • Dart et Flutter

    Langage de Flutter, avec les paquets de pub.dev.

    Le fichier pubspec.lock des projets.

  • Swift

    Langage d’Apple, avec Swift Package Manager.

    Le fichier Package.resolved des projets.

  • C et C++

    Langages système, avec les paquets Conan.

    En développement : le fichier conan.lock, quand l’OSV inclura les avis de ConanCenter.

Serveurs et bases de données

Ceux qui sont installés hors du gestionnaire de paquets, compilés dans /usr/local ou /opt, comme dans plusieurs images officielles et dans celles de Bitnami, et les paquets du dépôt propre à l’éditeur, que les avis de la distribution ne couvrent pas. La version est lue dans le fichier lui-même ou dans le paquet, sans rien exécuter.

  • Apache HTTP Server

    Serveur web open source.

    Lu directement dans httpd, comme celui de l’image officielle.

  • nginx

    Serveur web et proxy inverse.

    Lu directement dans le binaire, comme dans les images Bitnami, et dans le paquet de nginx.org, comme dans l’image officielle.

  • Apache Tomcat

    Serveur d’applications Java.

    Lu dans les notes de version de l’installation, comme dans l’image officielle.

  • Redis

    Base de données en mémoire, utilisée comme cache et comme file d’attente.

    Lu directement dans redis-server, comme celui de l’image officielle.

  • PostgreSQL

    Base de données relationnelle.

    Lu directement dans postgres, comme celui de l’image officielle Alpine, et dans le paquet du PGDG, comme dans l’image officielle Debian.

  • MariaDB

    Base de données relationnelle dérivée de MySQL.

    Le paquet du dépôt de MariaDB, comme dans l’image officielle.

  • MySQL

    Base de données relationnelle d’Oracle.

    En développement : la version du binaire mysqld, quand l’OSV inclura les avis de MySQL.

  • MongoDB

    Base de données orientée documents.

    Le paquet du dépôt de MongoDB, comme dans l’image officielle.

  • RabbitMQ

    File de messages entre applications.

    RabbitMQ dans /opt/rabbitmq, comme dans l’image officielle, et le paquet rpm de l’éditeur.

Services réseau

Le module Rede (Réseau) identifie ces services d’après la réponse de chacun, sans s’authentifier. Ce qui est exposé sans protection devient un constat.

  • SSH

    Accès à distance aux serveurs.

    Version d’après la bannière du service.

  • HTTP et HTTPS

    Sites, API et tableaux de bord.

    Serveur et version d’après l’en-tête de la réponse.

  • Certificats TLS

    Le chiffrement des services.

    Certificat invalide ou proche de l’expiration.

  • Docker Engine

    L’API qui contrôle Docker.

    Exposée sans authentification ou sans chiffrement.

  • Registre d’images

    L’endroit où sont stockées les images des conteneurs.

    Un registre sans chiffrement devient un constat.

  • MySQL et MariaDB

    Bases de données relationnelles.

    Version d’après le handshake du protocole.

  • PostgreSQL

    Base de données relationnelle.

    Identifié d’après la réponse à la demande TLS.

  • Redis

    Base de données en mémoire.

    Ouvert sans mot de passe, il devient un constat.

  • MongoDB

    Base de données orientée documents.

    Identifié d’après la réponse à la commande hello.

  • Elasticsearch et OpenSearch

    Recherche et analyse de données.

    Ouvert sans authentification, il devient un constat.

  • Kubernetes

    L’API du cluster, le kubelet des nœuds et etcd.

    Un accès anonyme ou exposé devient un constat.

  • Jenkins

    Serveur d’intégration continue.

    Version d’après l’en-tête X-Jenkins.

  • Grafana

    Tableaux de bord de supervision.

    Identifié d’après le titre de la page.

  • Kibana

    Tableau de bord d’analyse d’Elasticsearch.

    Identifié d’après le titre de la page.

  • Portainer

    Administration de conteneurs depuis le navigateur.

    Identifié d’après le titre de la page.

  • FTP

    Transfert de fichiers.

    La version d’après la bannière et si FTPS (AUTH TLS) est proposé ; sans lui, l’identifiant, le mot de passe et les fichiers circulent en clair.

  • SMTP

    Envoi d’e-mails.

    La version d’après la bannière, STARTTLS et l’authentification proposée avant le chiffrement.

  • RDP

    Bureau à distance de Windows.

    L’exposition du service et l’exigence de NLA, d’après la négociation initiale, sans identifiants.

  • Prometheus

    Collecte de métriques.

    L’API et la configuration ouvertes sans authentification, et les métriques des exportateurs, avec la version.

  • RabbitMQ

    File de messages entre applications.

    La version d’après le protocole AMQP, sans authentification, la connexion sans TLS et l’interface d’administration exposée.

Conteneurs, Kubernetes et cloud

  • Docker

    Plateforme de conteneurs.

    Les conteneurs en cours d’exécution sur les machines, via le parc, et les images enregistrées avec docker save ; pour chaque paquet de l’image, la couche qui l’a apporté et si la correction se fait dans l’image de base ou dans le Dockerfile.

  • Dockerfile

    La recette de construction de l’image.

    Les mauvaises pratiques, comme l’exécution en root, un secret dans ENV et la copie du projet entier.

  • Images de registre

    Docker Hub, GitHub Container Registry et d’autres registres compatibles.

    L’image est lue directement dans le registre, sans Docker, avec la vérification de la signature cosign.

  • Kubernetes

    Orchestrateur de conteneurs.

    Manifestes YAML et JSON : privilèges, root, hostPath, limites et jeton du compte de service.

    En développement : la lecture des clusters enregistrés dans Nuvem (Cloud).

  • Amazon Web Services

    Le cloud d’Amazon.

    EC2, security groups, ECR et EKS, en lecture seule.

  • Microsoft Azure

    Le cloud de Microsoft.

    En développement : la lecture des comptes, au même format qu’AWS. L’enregistrement fonctionne déjà.

  • Google Cloud

    Le cloud de Google.

    En développement : la lecture des projets, au même format qu’AWS. L’enregistrement fonctionne déjà.

  • Helm

    Gestionnaire de paquets de Kubernetes.

    Les charts, générés par helm template, avec les mêmes contrôles que les manifestes, dans l’analyse du projet.

  • Terraform

    Infrastructure en tant que code.

    Les fichiers .tf, le terraform.tfvars et le plan en JSON : ports d’administration et de base de données ouverts sur Internet, base de données et bucket publics, et API du cluster ouverte.

  • Podman

    Conteneurs sans service en arrière-plan.

    Les conteneurs Podman sur les machines du parc, y compris ceux sans root de l’utilisateur de la connexion.

Formats et intégrations

  • CycloneDX

    Format ouvert de SBOM, de l’OWASP.

    Génère le SBOM des analyses et lit ceux d’autres outils, y compris le VEX dans ce format.

  • SPDX

    Format de SBOM de la Linux Foundation.

    Génère le SBOM des analyses et lit ceux d’autres outils.

  • OpenVEX

    Déclare les vulnérabilités qui ne s’appliquent pas.

    Ce qui est déclaré non affecté ou corrigé est retiré du rapport.

  • SARIF

    Format de résultats d’analyse statique.

    Les constats apparaissent dans l’onglet Security de GitHub.

  • GitHub Actions

    L’automatisation de GitHub.

    Une action dédiée, qui exécute DockScan dans la CI et fait échouer le build quand l’analyse échoue selon la politique.

  • Dépôts de code

    Dossiers et dépôts Git d’un projet.

    Le projet entier en une seule fois, par dossier, .zip ou URL Git : dépendances, Dockerfiles, manifestes, charts, Terraform, secrets et licences.

  • Licences

    Les licences logicielles des paquets.

    Celles des dépendances de l’application : AGPL et SSPL, GPL et copyleft faible, comme LGPL et MPL.

  • Jira

    Gestion des tâches d’Atlassian.

    Ouvre un ticket à partir du constat, avec l’actif, le paquet et la correction.

  • Notifications à l’équipe

    E-mail et messageries.

    À la fin de l’analyse, prévient par webhook (Slack, Teams, Discord) ou par e-mail lorsqu’un constat important apparaît.

D’où viennent les données

  • OSV

    Base ouverte de vulnérabilités, maintenue par Google.

    Les avis des paquets, des distributions et de Bitnami.

  • KEV

    Catalogue de la CISA, l’agence de cybersécurité des États-Unis, avec les vulnérabilités exploitées.

    Marque les constats qui font l’objet d’une exploitation active.

  • EPSS

    Score du FIRST pour la probabilité d’exploitation dans les 30 prochains jours.

    Ordonne les constats par priorité.

  • endoflife.date

    Dates de fin de support des systèmes et des programmes.

    Signale quand la version du système sort du support.

  • Base de sécurité d’Alpine

    La liste des correctifs publiée par Alpine lui-même.

    Vérifie les paquets Alpine quand l’OSV enregistre une correction erronée.

  • Maven Central

    Le dépôt public des bibliothèques Java.

    Identifie les jars sans les données Maven d’après l’empreinte du fichier.

  • deps.dev

    Base ouverte de Google avec les données des paquets publiés.

    Complète la licence des dépendances qui n’en avaient pas dans le fichier.

Les marques appartiennent à leurs propriétaires respectifs et n’apparaissent que pour identifier chaque projet. Les logos proviennent du projet Simple Icons et des projets eux-mêmes ; les protocoles et les éléments sans logo propre apparaissent avec une icône générique. Les éléments en développement apparaissent avec leur logo en gris.

Mode d’emploi

Découvrez le déroulement d’une analyse et le rôle de chaque fonction de l’interface. Les chapitres suivants détaillent les étapes, avec l’écran correspondant à chacune.

Le parcours complet, pas à pas

  1. Choisissez la cible

    Ouvrez Novo scan (Nouveau scan) pour saisir les adresses IP des machines. Pour les IP, les ports et les services, suivez le tutoriel réseau.

  2. Renseignez l’entrée et la politique

    Saisissez les adresses IP et configurez l’accès SSH dans Frota (Parc). Définissez la sévérité qui doit faire échouer le scan et indiquez si vous voulez comparer avec une analyse précédente.

  3. Lancez et suivez

    Cliquez sur « Iniciar varredura por IP » (Lancer le scan par IP) ou, pour le réseau, sur « Iniciar varredura » (Lancer le scan). Attendez la fin et vérifiez les messages d’erreur et les avertissements de couverture.

  4. Examinez les constats

    Dans Resultados (Résultats), filtrez les éléments et lisez l’emplacement, les détails et la recommandation. Les états « Passou » (Réussi) et « Falhou » (Échoué) se rapportent à la politique configurée.

  5. Corrigez et relancez l’analyse

    Modifiez la cible et lancez un autre scan compatible. Utilisez Comparar scans (Comparer les scans) pour repérer les éléments nouveaux, persistants et ceux qui ne sont plus signalés.

  6. Conservez le résultat et créez une routine

    Exportez le rapport au format voulu. Pour répéter l’analyse, configurez une planification.

Ce que fait chaque fonction du menu

Painel (Tableau de bord)

Affiche les constats les plus récents par cible, les scans récents et les éléments urgents.

Consultez le résumé et ouvrez une analyse dans « Scans recentes » (Scans récents). Cliquez sur le nombre d’une sévérité, ou sur « Ver em Achados » (Voir dans Constats), pour ouvrir ces constats déjà filtrés. Voir les indications.

Novo scan (Nouveau scan)

Analyse le système et les conteneurs des machines sélectionnées par IP.

Saisissez les adresses IP, vérifiez la politique et lancez le scan. Voir les étapes.

Resultados (Résultats)

Conserve l’historique et permet d’examiner les constats de chaque analyse.

Repérez le scan, ouvrez le résultat, appliquez des filtres et lisez les détails. Voir les étapes.

Achados (Constats)

Réunit dans un tableau les constats du dernier scan de chaque cible, avec une requête proche du SQL, l’état de chaque constat d’après l’historique, un tri avec échéance, des tags et des vues enregistrées.

Cliquez dans la zone de requête, choisissez le champ, l’opérateur et les valeurs, puis lancez la requête. Voir les étapes.

Inventário (Inventaire)

Rassemble les machines, les conteneurs et les services issus des scans sur une carte et dans une liste. Les machines découvertes dans le cloud y figurent par leur IP, aux côtés de celles du parc et du réseau.

Cliquez sur une machine pour déplier ses éléments, sélectionnez une ressource pour en voir les détails et utilisez les filtres pour trouver une IP ou un service.

La carte s’appuie sur les données enregistrées. Les états historiques et les dates aident à repérer les collectes anciennes ou incomplètes. Les plages sont des regroupements visuels des adresses IP.

Frota (Parc)

Enregistre l’inventaire des hôtes dont les conteneurs seront analysés.

Ajoutez les hôtes, enregistrez et utilisez « Configurar varredura » (Configurer le scan). Voir les étapes.

Nuvem (Cloud)

Enregistre des comptes cloud et des clusters Kubernetes avec des identifiants en lecture seule. La lecture d’AWS fonctionne déjà ; les autres fournisseurs arriveront lors des prochaines étapes.

Choisissez le fournisseur, remplissez les champs, testez la connexion et utilisez « Descobrir agora » (Découvrir maintenant). Voir les étapes.

Buscar CVE (Rechercher une CVE)

Vérifie une CVE ou une GHSA en direct sur les adresses IP indiquées, avec une collecte à jour par SSH.

Voir les étapes de l’investigation.

Allowlist (Liste d’autorisation)

Écarte les constats déjà évalués des prochaines analyses et de l’évaluation de la politique.

Saisissez une entrée par ligne, vérifiez sa portée et enregistrez. Voir les étapes.

Rede (Réseau)

Regroupe le scan réseau, les hôtes, les services, l’exposition de Docker, les registres, les certificats TLS et les constats réseau.

Commencez par « Varrer a rede » (Scanner le réseau) et examinez les résultats dans les écrans du module. Voir les étapes.

Agendamentos (Planifications)

Répète des analyses selon un intervalle et une entrée enregistrés.

Définissez le nom, le type, l’intervalle, l’heure, la cible et la politique. Voir les étapes.

Baselines (Références)

Compare des analyses compatibles et montre comment les constats ont évolué.

Sélectionnez le scan actuel et la référence, puis passez en revue les groupes. Voir les étapes.

Auditoria (Audit)

Permet de consulter les journaux d’accès et d’opérations de l’interface.

Ouvrez le menu et recherchez par utilisateur, action, cible ou résultat. Voir les étapes.

Configurações (Paramètres)

Affiche les informations de l’instance, les limites d’envoi et les options réseau.

Vérifiez la connexion et ajustez le périmètre et les options réseau. Voir les étapes.

Les écrans de Rede

Painel de rede (Tableau de bord réseau)

Résume les scans sélectionnés. Choisissez les analyses et filtrez par IP ou par sévérité pour consulter les indicateurs.

Varrer a rede (Scanner le réseau)

Crée une analyse. Indiquez les cibles autorisées, vérifiez le profil, les ports et les modules, puis cliquez sur « Iniciar varredura ».

Hosts (Hôtes)

Organise les observations par hôte. Sélectionnez un scan et ouvrez l’hôte pour examiner les ports, les services et les preuves.

Serviços (Services)

Liste les services identifiés. Sélectionnez le scan, filtrez la liste et vérifiez les données observées.

Exposição do Docker (Exposition de Docker)

Rassemble les observations sur les API Docker. Vérifiez les preuves d’exposition et les constats associés.

Registries (Registres)

Rassemble les données observées dans les registres. Choisissez le scan et consultez les entrées et leurs preuves.

Certificados TLS (Certificats TLS)

Permet d’examiner les observations TLS. Vérifiez les données du certificat et les problèmes signalés par l’analyse.

Achados de rede (Constats réseau)

Rassemble les constats réseau. Filtrez par cible, port, service ou sévérité ; ouvrez un élément et enregistrez le tri avec un commentaire.

Em andamento (En cours)

Affiche la progression des analyses actives. Ouvrez les résultats en direct ou utilisez les commandes de pause, de reprise et d’arrêt.

Histórico (Historique)

Permet de retrouver les analyses précédentes. Filtrez l’historique et utilisez les actions pour ouvrir, relancer, comparer, exporter ou supprimer une analyse.

Comparar varreduras (Comparer les scans)

Compare la couverture et les observations de deux analyses. Choisissez les scans et examinez aussi les éléments sans couverture comparable.

Perfis (Profils)

Enregistre des combinaisons de ports, de découverte et d’audits. Créez un profil ou dupliquez-en un existant, ajustez les champs et enregistrez.

Allowlist : comment ajouter une exception
  1. Ouvrez « Allowlist » dans le menu.
  2. Saisissez une règle, un emplacement de paquet ou un identifiant par ligne. Les lignes commençant par # servent aux commentaires.
  3. Vérifiez la saisie et cliquez sur « Salvar allowlist » (Enregistrer l’allowlist).
  4. Lancez un nouveau scan pour appliquer la modification. L’historique antérieur reste inchangé.

Une entrée de paquet peut écarter plusieurs vulnérabilités. Vérifiez la portée de l’exception avant d’enregistrer.

Auditoria : comment retrouver une activité
  1. Ouvrez « Auditoria » dans le menu.
  2. Remplissez « Buscar atividade » (Rechercher une activité) avec un utilisateur, une action, une cible ou un résultat.
  3. Vérifiez la date, l’utilisateur, l’action, la cible, l’IP et le résultat de l’activité trouvée.
  4. Effacez la recherche pour revenir à la liste disponible.
Configurações : ce qu’il faut vérifier et comment régler le réseau
  1. Ouvrez « Configurações » pour consulter la version, la connexion et les limites d’envoi.
  2. Dans « Configurações de rede » (Paramètres réseau), vérifiez les périmètres autorisés, les exclusions et les limites de l’analyse.
  3. Contrôlez aussi le format des rapports, les preuves et les préférences de l’interface.
  4. Cliquez sur « Salvar configurações de rede » (Enregistrer les paramètres réseau). Les modifications du périmètre et des limites globales exigent qu’aucun scan ne soit en cours.
  5. Dans « Jira » et « Avisos à equipe » (Notifications à l’équipe), réservés aux administrateurs, configurez l’ouverture de tickets à partir des constats et les notifications à la fin des scans, par webhook ou par e-mail. « Testar a conexão » (Tester la connexion) et « Enviar um teste » (Envoyer un test) permettent de vérifier avant utilisation, et le résultat de chaque notification est consigné dans Auditoria (Audit).

Lisez attentivement la confirmation avant de réduire la durée de conservation : ce changement peut supprimer d’anciens scans réseau et leurs rapports.

Achados de rede : comment enregistrer le tri

Indiquez les adresses des machines. DockScan collecte les données par SSH et identifie automatiquement les paquets installés.

Que collecte le scan ?

Le scan lit les paquets et la configuration du système, les conteneurs et les données disponibles sur les processus et les ports. Le résultat signale les échecs d’accès et les parties de la collecte restées incomplètes.

« Pular consulta de CVEs » (Ignorer la recherche de CVE) désactive la recherche de vulnérabilités. « Pular KEV e EPSS » (Ignorer KEV et EPSS) désactive cet enrichissement. L’absence de constats dans une collecte incomplète n’exclut pas la présence de vulnérabilités.

Quelle différence entre « Falhou » (Échoué) et « Erro na análise » (Erreur d’analyse) ?

« Falhou » et « Passou » sont le résultat de la politique : l’analyse est terminée, et un constat a atteint, ou non, le seuil configuré. « Erro na análise » est une défaillance technique : la collecte ne s’est pas terminée.   1. Ouvrez « Achados » dans le menu

    Le tableau s’ouvre sur tous les constats, classés du plus urgent au moins urgent : d’abord par priorité, puis ceux qui font l’objet d’une exploitation active (KEV), par sévérité et par probabilité d’exploitation (EPSS).

    La liste affiche les champs. Survolez un champ pour ouvrir ses options à côté : choisissez l’opérateur, cochez une ou plusieurs valeurs et cliquez sur « Adicionar à consulta » (Ajouter à la requête). Cliquez ensuite sur « Consultar » (Consulter) ou appuyez sur Entrée. Si vous connaissez déjà le langage, vous pouvez saisir la requête directement.

Cliquez sur l’en-tête d’une colonne pour classer le tableau. Lorsque Jira est configuré, « Abrir ticket no Jira » (Ouvrir un ticket dans Jira) crée le ticket du constat. De là, vous faites le tri et passez au constat précédent ou suivant de la requête ; Échap ou « Fechar » (Fermer) ramène au tableau.

    Cochez les constats dans la première colonne. Comment DockScan définit-il la priorité ?

Chaque vulnérabilité reçoit l’une des quatre priorités, et l’écran affiche les raisons de chacune :

  1. Corrigir agora (Corriger maintenant) : exploitée activement (KEV) ; probabilité d’exploitation (EPSS) de 10 % ou plus avec le paquet en cours d’utilisation ou accessible depuis le réseau ; ou critique et accessible depuis le réseau.
  2. Esta semana (Cette semaine) : EPSS de 10 % ou plus ; ou critique ou haute qui a un EPSS de 1 % ou plus, est en cours d’utilisation ou est accessible depuis le réseau.
  3. Planejar (Planifier) : les autres critiques et hautes, celles qui ont un EPSS de 1 % ou plus et les moyennes qui ont déjà une correction.
  4. Acompanhar (Suivre) : le reste.

Un paquet installé qu’aucun processus ne charge descend d’un niveau. Les constats de configuration, sans CVE, suivent la sévérité. Dans une requête, utilisez prioridade = agora, em_uso ou exposto.

Quels champs puis-je interroger ?

severidade, cve, regra, titulo, pacote, versao, ecossistema, correcao, corrigivel, fonte, ativo, ip, porta, container, local, epss, kev, prioridade, em_uso, exposto, camada, novo, visto_em, estado, triagem, primeiro_visto, corrigido_em, prazo, tag et scan. L’aide « Como consultar » (Comment interroger), disponible à l’écran, décrit chacun d’eux.

Un champ de type oui ou non utilisé seul vaut « sim » (oui) : kev équivaut à kev = sim. Les dates acceptent 2026-11-01, -7d, +30d, -24h, hoje (aujourd’hui) et ontem (hier). L’EPSS accepte 0.1 ou 10%.

Comment fonctionne l’échéance du tri ?

Les statuts Revisado, Falso positivo et Risco aceito peuvent avoir une échéance de deux ans au maximum. Une fois l’échéance passée, le constat redevient ouvert et réapparaît dans le tableau avec la mention « Prazo vencido » (Échéance dépassée). Pour passer en revue les exceptions qui arrivent bientôt à échéance, lancez la requête triagem != aberto e prazo < +30d.

Comment créer des tags et des vues enregistrées ?

Un tag a le format catégorie:valeur, par exemple ambiente:producao ou time:plataforma, et il est défini par une requête. Écrivez la requête qui sélectionne les constats, cliquez sur « Criar tag com esta consulta » (Créer un tag avec cette requête) et indiquez la catégorie et la valeur. Tout constat qui correspond à la requête reçoit le tag, y compris ceux des prochains scans. Filtrez ensuite avec tag = ambiente:producao ou tag = ambiente:*, ou regroupez par tag. Les tags figurent dans le panneau « Tags », avec le nombre de constats que chacun marque.

Une vue enregistrée conserve la requête et le regroupement sous un nom. Utilisez « Salvar como visão » (Enregistrer comme vue), puis choisissez la vue plus tard dans « Visões salvas » (Vues enregistrées). Les tags et les vues s’appliquent à tous les utilisateurs de cette instance.

Qu’est-ce que le plan de correction ?

Dans « Agrupar por », choisissez « Plano de correção » (Plan de correction). Chaque ligne correspond à un paquet installé, avec son nombre de vulnérabilités, la sévérité la plus élevée, les actifs concernés et la version vers laquelle mettre à jour. Mettre à jour un paquet de la liste corrige d’un coup toutes les vulnérabilités de la ligne.

Puis-je interroger depuis le terminal ?

Oui, avec le même langage qu’à l’écran, en lisant les données de l’interface :

dockscan achados severidade >= alta e kev --data-dir ~/.dockscan
dockscan achados estado = novo --formato csv > novos.csv

Sans --formato, vous obtenez un tableau ; avec json ou csv, les mêmes données que l’export depuis l’écran.

La requête a renvoyé une erreur

Le message indique ce qui manque et à quelle position, et le curseur se place à l’endroit du problème. Les erreurs les plus courantes sont un nom de champ erroné, un opérateur qui ne s’applique pas au champ (comme > sur kev) et des guillemets ou des parenthèses non fermés.

Suivre les corrections

Relancez l’analyse après avoir modifié la cible et comparez les résultats pour savoir ce qui a changé.

  1. Lancez un nouveau scan de la même cible

    Utilisez le même type d’analyse et le même nom de cible. Conservez la même sélection d’adresses IP et les mêmes options de couverture.

  2. Ouvrez « Comparar scans » (Comparer les scans)

    Sur la page d’un résultat terminé, cliquez sur Comparar scans. Vous pouvez aussi ouvrir Baselines (Références) dans le menu. Sélectionnez le scan actuel et la référence compatible.

  3. Passez en revue les trois groupes

    Les Novos (Nouveaux) sont apparus dans le scan actuel. Les Persistentes (Persistants) sont toujours présents. Les Corrigidos (Corrigés) figuraient dans la référence et n’apparaissent pas dans le résultat actuel. Ouvrez les éléments pour comprendre le changement.

Avant de comparer

Une recherche désactivée, une erreur de collecte ou une modification de l’allowlist peut changer les résultats. « Corrigido » (Corrigé) signifie que le constat n’est plus signalé dans cette comparaison. Vérifiez les preuves et les avertissements des deux scans.

Comment gérer une exception avec l’Allowlist ?

Ouvrez Allowlist (Liste d’autorisation), saisissez une règle, un emplacement de paquet ou un identifiant par ligne, puis cliquez sur Salvar allowlist (Enregistrer l’allowlist). Les lignes qui commencent par # sont des commentaires.

Les entrées s’appliquent aux prochains scans et retirent les constats correspondants de l’évaluation d’échec. L’historique antérieur reste inchangé. Vérifiez la portée de chaque entrée : un paquet peut regrouper plusieurs vulnérabilités.

Analyser votre parc

Enregistrez les hôtes pour analyser les conteneurs en cours d’exécution et leur configuration, à partir de l’inventaire enregistré.

  1. Ouvrez « Frota » (Parc) et remplissez l’inventaire

    Indiquez une adresse IP par ligne, avec les options d’accès SSH. Le serveur DockScan doit pouvoir joindre les hôtes par SSH, disposer d’un accès par clé ou via le coffre-fort d’identifiants et avoir l’autorisation d’effectuer les lectures. Le coffre-fort se trouve sur la page Frota elle-même.

  2. Enregistrez et lancez l’analyse

    Dans le résultat, ouvrez les hôtes et vérifiez les constats de la machine et des conteneurs. Contrôlez aussi les échecs d’accès et les avertissements de collecte. Revenez à « Frota » pour consulter le dernier scan.

  4. Voyez les machines dans Inventário

    Après l’analyse, « Inventário » (Inventaire) montre les machines, les conteneurs et les services trouvés, sur une carte groupée par plage d’IP ou dans une liste. Cliquez sur une machine pour ouvrir ses conteneurs et ses services, et utilisez la recherche et les filtres pour trouver une IP.

Comment configurer le coffre-fort SSH
  1. Dans Frota, rendez-vous à la section « Cofre de acesso SSH » (Coffre-fort d’accès SSH).
  2. Indiquez le nom, l’utilisateur, le mot de passe et le périmètre autorisé. Ne cochez sudo que si ce compte est configuré pour l’utiliser.
  3. Cliquez sur « Salvar credencial » (Enregistrer l’identifiant). Le mot de passe est effacé du champ et l’interface ne le renvoie jamais.

L’identité SSH est enregistrée lors de la première connexion. Si elle change, vérifiez ce changement avant de retirer l’entrée de la liste des identités connues.

Ce qui est lu sur chaque machine

La collecte n’utilise que ce que la machine possède déjà : des commandes système et des fichiers de /proc et /etc. Inutile d’installer Python ou un agent. Sur une machine minimale, sans ss ni ps, les ports et les processus sont lus directement depuis le noyau.

  1. Paquets du système : Debian et Ubuntu (dpkg), Alpine (apk), Rocky Linux et AlmaLinux (rpm). Les autres distributions RPM, comme Red Hat et Amazon Linux, apparaissent comme non vérifiées, car l’OSV ne fournit pas leurs avis de sécurité.
  2. Les avis de Debian, d’Ubuntu et de Rocky citent le paquet source : une vulnérabilité d’OpenSSL qui concerne libssl3 apparaît sous openssl.
  3. Le noyau est évalué d’après la version en cours d’exécution, pas d’après les paquets installés. Le constat indique le total des CVE et liste celles qui comptent maintenant : celles qui font l’objet d’une exploitation active, celles dont la probabilité d’exploitation est de 1 % ou plus, celles publiées ces derniers jours et celles de sévérité critique ou haute qu’un noyau déjà installé corrige au prochain démarrage.
  4. Les paquets des langages (pip, npm, gems, Composer et NuGet) et les bibliothèques Java (.jar, .war, .ear), dans les conteneurs et sur la machine, y compris dans /home et /root ; les binaires Go dans les deux (sur la machine, seulement ceux compilés avec Go 1.18 ou plus récent) et les binaires Rust dans les conteneurs. Dans un conteneur sans shell, les paquets des langages proviennent des dossiers de l’application, copiés avec docker cp.
  5. Les programmes installés hors du gestionnaire de paquets, comme node, python et redis dans les images officielles : la version est lue dans le fichier lui-même, sans rien exécuter. La liste figure dans Ce que DockScan reconnaît.
  6. Les conteneurs Docker et Podman. Avec Podman sans root, ce sont les conteneurs de l’utilisateur de la connexion SSH qui sont lus.
  7. La fin de support du système de la machine et de chaque conteneur.
  8. Pour chaque paquet vulnérable, si un processus utilise actuellement ses fichiers. Un binaire Go à l’arrêt réduit l’exposition ; pour les bibliothèques Java, DockScan se limite à confirmer l’utilisation, car un .war décompressé par le serveur est utilisé sans rester ouvert.
Comment examiner une CVE
  1. Ouvrez « Buscar CVE » (Rechercher une CVE) dans le menu de l’outil.
  2. Indiquez les adresses IP et un identifiant CVE ou GHSA.
  3. Cliquez sur « Verificar CVE nos IPs » (Vérifier la CVE sur les IP). Les données sont collectées par SSH sur les machines sélectionnées.
  4. Lisez les occurrences, la date de la collecte, les avertissements et les preuves d’utilisation. Une collecte incomplète ne permet pas d’écarter une cible.

Les paquets sont identifiés automatiquement pendant la collecte par IP.

Explorer le réseau

Le module Rede (Réseau) identifie les ports et les services et rassemble les preuves d’exposition sur les cibles autorisées.

  1. Vérifiez les périmètres autorisés

    Dans Configurações → Configurações de rede (Paramètres → Paramètres réseau), vérifiez « Escopos de rede autorizados (IP/CIDR) » (Périmètres réseau autorisés). N’incluez que des réseaux que vous êtes autorisé à analyser. La valeur par défaut autorise le loopback.

  2. Ouvrez « Rede → Varrer a rede » (Réseau → Scanner le réseau)

    Donnez un nom au scan. Dans IP, range, CIDR ou múltiplos alvos (IP, plage, CIDR ou cibles multiples), indiquez les adresses IP et les réseaux. Pour faire un essai sur la machine du serveur, utilisez 127.0.0.1. Vous pouvez aussi importer une liste .txt dans « Importar alvos » (Importer des cibles).

    Renseignez les exclusions si nécessaire. Vérifiez l’estimation du nombre de cibles et le périmètre autorisé affichés dans le formulaire.

  3. Choisissez le profil et vérifiez les ports

    Dans « Configuração da varredura » (Configuration du scan), sélectionnez le « Perfil » (Profil) et vérifiez les « Portas » (Ports). Contrôlez le délai d’expiration, la vitesse et les modules « Detectar serviços » (Détecter les services), « Detectar Docker » (Détecter Docker), « Auditar registries » (Auditer les registres) et « Analisar TLS » (Analyser TLS).

  4. Confirmez l’autorisation et cliquez sur « Iniciar varredura » (Lancer le scan)

    Suivez la progression sur la page du scan. Utilisez « Pausar » (Mettre en pause), « Retomar » (Reprendre) ou « Parar » (Arrêter) pour gérer son exécution. Après un arrêt, les résultats partiels restent disponibles.

Où consulter ensuite

« Em andamento » (En cours) affiche les tâches actives. « Histórico » (Historique) conserve les analyses précédentes. Utilisez « Hosts » (Hôtes) et « Serviços » (Services) pour examiner les hôtes et les services trouvés.

Comment lire la couverture

Sur la page du scan, basculez « Visualização » (Affichage) entre hôtes, ports, couverture TCP, services et constats. Consultez « Configuração e limitações » (Configuration et limites) pour comprendre la portée de la collecte.

À propos de la couverture

Un timeout est un résultat non concluant

Rien ne prouve qu’un port qui ne répond pas soit fermé. De même, rien ne prouve qu’un hôte qui ne répond pas soit éteint. Vérifiez les états de couverture avant de comparer ou de clore l’investigation.

Quels services le scan reconnaît-il ?

En plus de SSH, HTTP, TLS, Docker, des registres, Redis, PostgreSQL, MongoDB et MySQL, le scan identifie ces services d’après leur réponse, sans authentification et sans aucune commande qui modifie quoi que ce soit :

  1. FTP : la version d’après la bannière et si FTPS est proposé. Sans lui, l’identifiant, le mot de passe et les fichiers circulent en clair.
  2. SMTP : la version, STARTTLS et l’authentification proposée avant le chiffrement.
  3. RDP : l’exposition du service et l’exigence de NLA avant la session.
  4. RabbitMQ : la version d’après le protocole AMQP, la connexion sans TLS et l’interface d’administration sur le port 15672.
  5. Prometheus : l’API ouverte sans authentification et les métriques des exportateurs, comme node_exporter.

Le profil « Network Services Scan » (Scan des services réseau) inclut déjà les ports de ces services.

Comment comparer deux scans réseau ?

Ouvrez « Comparar varreduras » (Comparer les scans) dans le menu Rede ou utilisez « Comparar » (Comparer) dans le résultat. Sélectionnez les deux analyses et passez en revue les éléments nouveaux, supprimés, modifiés et inchangés.

Les éléments sans couverture comparable apparaissent comme « NotComparable » (non comparable). Vérifiez les cibles, les ports et les modules avant de considérer un service comme supprimé ou un risque comme résolu.

Connecter le cloud

Le module cloud lit les comptes AWS pour repérer ce qui expose vos conteneurs : machines, règles de pare-feu, registres et clusters. Azure, Google Cloud et Kubernetes peuvent déjà être enregistrés ; leur lecture arrivera lors des prochaines étapes.

  1. Créez un identifiant en lecture seule

    Lorsque vous choisissez le fournisseur, l’écran affiche l’autorisation minimale et la marche à suivre pour créer l’identifiant. N’utilisez jamais la clé d’un utilisateur administrateur.

  2. Ouvrez « Nuvem » (Cloud) et choisissez le fournisseur

    Donnez un nom au compte et remplissez les champs. Les régions, abonnements, projets ou namespaces définissent ce qui peut être lu.

  3. Enregistrez et cliquez sur « Testar conexão » (Tester la connexion)

    Sur AWS, le test vérifie l’accès directement dans le cloud et affiche l’identité utilisée. Pour les autres fournisseurs, il confirme que le compte a été validé et enregistré.

Les constats vont dans l’écran Achados (Constats) avec fonte = cloud, et les machines dans Inventário (Inventaire). Si une région ne peut pas être lue, le scan est marqué incomplet et indique laquelle.

  5. Modifiez ou supprimez au besoin

    Dans « Editar » (Modifier), un secret laissé vide conserve sa valeur actuelle. « Excluir » (Supprimer) efface le compte et ses secrets du serveur.

Sécurité

Les secrets sont chiffrés, mais stockés sur le serveur

Les identifiants sont chiffrés avec la clé du coffre-fort et ne réapparaissent jamais à l’écran. Toute personne disposant d’un accès administrateur au serveur DockScan peut les lire : n’enregistrez que des identifiants en lecture seule et, de préférence, avec une date d’expiration.

Pourquoi mon kubeconfig a-t-il été refusé ?

Par sécurité, le kubeconfig doit contenir le jeton ou le certificat intégré, ainsi que la CA du cluster dans certificate-authority-data. Sont refusés : l’authentification par exec ou auth-provider, qui exécuterait un programme sur le serveur DockScan ; les chemins de fichier, qui liraient des fichiers du serveur ; insecure-skip-tls-verify ; et les adresses sans https://.

Que recherche DockScan dans le cloud ?

Des ports d’administration ouverts sur Internet (API Docker, kubelet, etcd, API Kubernetes, registre et SSH), des règles qui ouvrent tous les ports, des registres accessibles en lecture anonyme ou avec un utilisateur administrateur, des tags mutables, une API de cluster ouverte, un cluster sans RBAC, des machines qui acceptent le service de métadonnées sans jeton et des workloads privilégiés.

Sur AWS, ces informations proviennent d’EC2 (machines et security groups), d’ECR et d’EKS, dans les régions enregistrées. Avec l’ARN du rôle, la clé sert uniquement à assumer ce rôle, pour une session de 15 minutes, et toutes les lectures passent par le rôle. Aucun appel ne crée ni ne modifie de ressources.

« Descobrir agora » (Découvrir maintenant) n’apparaît pas

Le bouton apparaît lorsque le fournisseur dispose déjà d’un connecteur et que son SDK est installé sur le serveur DockScan. Pour AWS, installez-le avec pip install "dockscan[cloud]". Le test de connexion signale aussi l’absence du SDK.

Planifier des analyses

Répétez une analyse à intervalles définis et consultez le résultat de chaque exécution dans l’historique.

  1. Ouvrez « Agendamentos » (Planifications) et nommez la routine

    Définissez l’intervalle en minutes et la première exécution. Pour une exécution quotidienne, utilisez 1440 minutes. L’interface accepte de 5 à 10080 minutes.

  2. Renseignez la cible et la politique

    Indiquez les adresses IP des machines et les critères d’échec. La sélection est enregistrée dans la routine, et l’accès SSH utilise les paramètres de Frota (Parc).

  3. Cliquez sur « Criar agendamento » (Créer la planification)

    La routine apparaît dans « Scans agendados » (Scans planifiés). Utilisez Executar agora (Exécuter maintenant) pour lancer une exécution manuelle, Pausar (Mettre en pause) pour suspendre les prochaines exécutions et Retomar (Reprendre) pour la réactiver. La suppression de la planification conserve les scans précédents.

Fonctionnement de la routine

La planification répète la collecte sur les adresses IP sélectionnées et identifie les données actuelles des machines. Ajouter d’autres adresses IP à l’inventaire n’élargit pas la cible d’une routine déjà créée.

Les analyses continuent-elles quand l’interface est fermée ?

Fermer l’onglet du navigateur n’arrête pas le serveur. Les routines continuent tant que le serveur DockScan tourne. Pour les exécuter quand le serveur web est arrêté, gardez actif le service autonome ci-dessous, avec le même répertoire de données que votre instance.

python -m dockscan agendador --data-dir ~/.dockscan

Sans le serveur ni ce service, les exécutions n’ont pas lieu. Au retour, l’exécution en attente est lancée, sans rattraper toutes les exécutions manquées.

Comptes et accès

Chaque personne se connecte avec son propre nom d’utilisateur et son mot de passe, et le rôle du compte définit ce qu’elle peut faire. Tout se gère dans Configurações (Paramètres).

  1. Connectez-vous avec votre nom d’utilisateur et votre mot de passe

    Sur l’écran de connexion, utilisez le nom d’utilisateur ou l’adresse e-mail du compte. « Manter conectado » (Rester connecté) garde la session ouverte jusqu’à 7 jours dans ce navigateur ; sans cette option, la session prend fin après 30 minutes d’inactivité ou au bout de 12 heures.

  2. À la première connexion, définissez votre mot de passe

    La personne qui crée le compte reçoit un mot de passe temporaire à vous transmettre. Lorsque vous vous connectez avec celui-ci, DockScan vous demande votre propre mot de passe avant d’ouvrir le moindre écran : au moins 12 caractères, et différent du nom d’utilisateur.

  3. Consultez votre profil dans Configurações

    Cliquez sur votre nom, en bas du menu. Le profil affiche le nom d’utilisateur, l’e-mail, le rôle et la date du dernier changement de mot de passe. Vous pouvez y modifier votre nom et votre e-mail, changer de mot de passe et voir les sessions ouvertes dans d’autres navigateurs, avec la possibilité de fermer chacune d’elles.

  4. Administrateur : créez les comptes de l’équipe

    Dans Usuários (Utilisateurs), indiquez le nom, le nom d’utilisateur et le rôle, puis cliquez sur « Criar usuário » (Créer l’utilisateur). Le mot de passe temporaire s’affiche une seule fois, avec le bouton Copiar (Copier) : transmettez-le par un canal sûr. Pour chaque compte, Editar (Modifier) change le nom, l’e-mail, le rôle et l’état actif du compte ; Redefinir senha (Réinitialiser le mot de passe) génère un nouveau mot de passe temporaire ; Excluir (Supprimer) retire l’accès.

  5. Activez la validation en deux étapes

    Dans Configurações, cliquez sur « Ativar a verificação em duas etapas » (Activer la validation en deux étapes), scannez le code QR avec une application d’authentification (Google Authenticator, Microsoft Authenticator, Authy ou 2FAS) et saisissez le code à 6 chiffres qu’elle affiche, avec votre mot de passe. Gardez les 10 codes de récupération affichés ensuite : chacun permet d’entrer une fois si vous perdez votre téléphone. Ensuite, la connexion demande le code après le mot de passe.

Rôles des comptes et ce que chacun permet
RôlePeut

Ce que le rôle ne permet pas n’apparaît pas à l’écran. Un changement de rôle prend effet immédiatement, sans que la personne ait à se reconnecter. DockScan ne laisse jamais le serveur sans administrateur actif, et personne ne peut modifier son propre rôle ni désactiver son propre compte.

Clés d’accès

Une clé se connecte en tant qu’administrateur, sans nom d’utilisateur ni mot de passe. Utilisez-la pour l’automatisation et pour récupérer l’accès ; pour les personnes, préférez un compte. Générez et révoquez les clés dans Configurações. La clé ne s’affiche qu’une seule fois.

Exiger la validation

Dans Usuários (Utilisateurs), l’administrateur choisit à qui exiger la validation en deux étapes : personne, les administrateurs ou tous les comptes. Ceux qui ne l’ont pas encore activée voient l’écran d’activation avant tout autre. Pour l’exiger d’un rôle qui est le vôtre, activez-la d’abord sur votre compte. Les clés d’accès ne demandent pas le code : gardez-les comme des mots de passe d’administrateur.

J’ai oublié mon mot de passe

Demandez à un administrateur d’utiliser Redefinir senha (Réinitialiser le mot de passe) sur votre compte : vous recevez un mot de passe temporaire et choisissez le vôtre à la connexion suivante. Vos sessions ouvertes sont fermées.

Si aucun administrateur n’est disponible, une personne ayant accès au serveur peut changer le mot de passe depuis le terminal, avec le même répertoire de données que l’instance :

dockscan usuarios senha --usuario SEU_USUARIO
J’ai perdu le téléphone de la validation en deux étapes

Sur l’écran de connexion, après le mot de passe, cliquez sur « Usar um código de recuperação » (Utiliser un code de récupération) et saisissez l’un des codes que vous avez gardés. Une fois connecté, générez de nouveaux codes, ou désactivez puis réactivez avec le nouveau téléphone.

Sans aucun code, demandez à un administrateur d’utiliser « Remover verificação » (Retirer la validation) sur votre compte : vos sessions sont fermées et la prochaine connexion ne demande que le mot de passe. Sans administrateur disponible, depuis le terminal du serveur :

dockscan usuarios remover-verificacao --usuario SEU_USUARIO
Le code n’est pas accepté

Le code change toutes les 30 secondes et chacun ne sert qu’une fois. Saisissez celui que l’application affiche maintenant et vérifiez que la date et l’heure du téléphone sont réglées automatiquement. Cinq codes faux de suite ramènent au mot de passe ; trop d’erreurs bloquent les nouvelles tentatives pendant 15 minutes.

Pourquoi ma session a-t-elle pris fin ?

La session prend fin après 30 minutes d’inactivité, au bout de 12 heures (7 jours avec « Manter conectado »), lorsque vous vous déconnectez, lorsqu’une autre de vos sessions la ferme depuis Configurações, lorsque vous changez de mot de passe (les autres sessions sont déconnectées) ou lorsqu’un administrateur réinitialise votre mot de passe ou désactive le compte. Redémarrer le serveur ne ferme pas les sessions. Activer la validation en deux étapes ferme aussi vos autres sessions, et un administrateur ferme les vôtres en retirant votre validation.

Le message « O papel não permite esta ação » (Le rôle ne permet pas cette action) s’affiche

Votre compte n’a pas l’autorisation nécessaire, par exemple pour modifier l’inventaire de Frota avec le rôle Analista. Demandez à un administrateur d’effectuer la modification ou d’ajuster votre rôle.

En développement

DockScan est un outil en cours de développement. Les écrans et les noms peuvent changer d’une version à l’autre. Ce chapitre présente ce qui vient d’arriver et ce qui suivra.

Nouveautés de cette version

  1. Rede (Réseau) : FTP, SMTP, RDP, RabbitMQ et Prometheus, avec l’absence de chiffrement, l’exigence de NLA, l’interface d’administration et les métriques ouvertes, ainsi que le profil Network Services Scan.
  2. Projet entier : via l’URL du dépôt Git ou le .zip, les dépendances, les Dockerfiles, les manifestes Kubernetes, les charts Helm, Terraform, les secrets et les licences, en une seule analyse.
  3. Couche de l’image : chaque paquet d’une image indique de quelle couche il vient et si la correction se fait dans l’image de base ou dans le Dockerfile.
  4. Podman sur les machines du parc, y compris sans root.
  5. Jira et notifications à l’équipe : le ticket à partir du constat et la notification par webhook ou par e-mail à la fin des scans.
  6. Plus de sources et de fichiers : la base de sécurité d’Alpine, les jars sans les données Maven grâce à Maven Central, uv.lock, pnpm-lock.yaml, bun.lock, gradle.lockfile, pom.xml, packages.lock.json, mix.lock, pubspec.lock et Package.resolved, et les paquets des dépôts des éditeurs (MongoDB, MariaDB, PGDG, nginx.org et RabbitMQ). Quand le paquet de l’éditeur porte le même nom que celui de la distribution, chaque CVE n’apparaît qu’une fois, dans le constat avec la version corrigée par l’éditeur.
  7. Anciens programmes Go et SBOM : ceux compilés avant Go 1.18 sont lus dans les images et les conteneurs. Dans le SBOM, les bibliothèques Java et .NET et les paquets de Rocky Linux et d’AlmaLinux sortent avec le bon type (Maven, NuGet et rpm), et les SBOM d’autres outils contenant ces paquets sont lus correctement.
  8. Ce que DockScan reconnaît : les systèmes, langages, programmes, services et formats qu’il lit, avec le logo de chacun, et ce qui est en développement.
  9. Plus d’emplacements lus : le noyau en cours d’exécution, les programmes installés hors du gestionnaire de paquets (comme node, python et redis dans les images officielles), les binaires Go et les bibliothèques Java de la machine, les dossiers /home et /root et les conteneurs sans shell.
  10. Fin de support : un système qui ne reçoit plus de correctifs de sécurité devient un constat, avec la version vers laquelle migrer.
  11. Priorité dans Achados : Corrigir agora (Corriger maintenant), Esta semana (Cette semaine), Planejar (Planifier) et Acompanhar (Suivre), selon l’exploitation active, la probabilité d’exploitation, l’utilisation et l’exposition sur le réseau.
  12. Validation en deux étapes : un code à 6 chiffres d’une application d’authentification, 10 codes de récupération et la possibilité de l’exiger des administrateurs ou de tous les comptes.
  13. Panneau du constat : cliquez sur la vulnérabilité pour voir le CVSS, l’EPSS, l’emplacement, la correction, la description de l’OSV, les autres actifs et l’historique, sans quitter la requête.
  14. Manuel en portugais, anglais, espagnol, français, allemand et japonais : choisissez la langue en haut de la page.
  15. Comptes et accès : un compte par personne, avec nom d’utilisateur et mot de passe, et les rôles Administrador (Administrateur), Analista (Analyste) et Leitura (Lecture) ; profil, changement de mot de passe et sessions ouvertes dans Configurações (Paramètres) ; les sessions sont conservées après un redémarrage du serveur.
  16. Achados (Constats) : état de chaque constat d’après l’historique (nouveau, actif, réapparu, corrigé), tri avec échéance et par lot, tags catégorie:valeur, vues enregistrées, plan de correction, classement par colonne et requêtes depuis le terminal.
  17. Nuvem (Cloud) : lecture d’AWS (EC2, security groups, ECR et EKS) sous forme de scan, avec les constats dans Achados et les machines dans Inventário (Inventaire).
  18. Frota (Parc) : un accès par IP dans l’inventaire, vérifié à l’enregistrement ; une machine retirée de l’inventaire disparaît aussi de l’écran Achados, et son historique reste dans Resultados (Résultats).
  19. Machines : paquets RPM de Rocky Linux et d’AlmaLinux, vulnérabilités rattachées au paquet source (libssl3 remonte désormais celles d’OpenSSL), utilisation des binaires Go et des bibliothèques Java, et collecte limitée à ce que la machine possède déjà.
  20. Painel (Tableau de bord) avec des raccourcis vers Achados, horaires avec fuseau horaire, et écrans Achados et Nuvem revus pour le clavier et les lecteurs d’écran.
  21. Resultados avec des noms clairs : « Falhou » (Échoué) et « Passou » (Réussi) pour la politique ; « Erro na análise » (Erreur d’analyse) s’affiche différemment, car il s’agit d’une défaillance technique.

Questions fréquentes

Vérifiez l’état de l’analyse avant d’interpréter le résultat.

Le scan n’a renvoyé aucun constat. Tout est-il sûr ?

Vérifiez que l’analyse est terminée, qu’aucun filtre ne masque d’éléments et qu’aucun avertissement d’échec ou de collecte incomplète n’apparaît. Vérifiez aussi si la recherche de CVE a été désactivée et si l’allowlist contient des entrées. L’absence de constat signifie que cette exécution n’a signalé aucun élément dans la couverture effectuée.

Une adresse IP a été refusée

Indiquez l’adresse IPv4 ou IPv6 de la machine, sans nom DNS, utilisateur, port ni plage. Si le port SSH est différent, configurez-le dans l’inventaire de Frota (Parc).

Impossible de se connecter à la machine

Vérifiez que le serveur DockScan peut joindre l’IP, que SSH est disponible et que l’identifiant du coffre-fort couvre cette adresse. Lisez l’erreur et les avertissements du scan pour identifier les parties de la collecte qui ont échoué.

Un hôte du parc a échoué

Vérifiez l’adresse, l’utilisateur, le port et le chemin de la clé dans l’inventaire. L’accès SSH et l’interrogation de Docker doivent fonctionner depuis la machine du serveur. Lisez les avertissements par hôte ; un échec d’accès peut empêcher la collecte sur cette cible.

Le scan réseau a rejeté ma cible

Vérifiez que vous avez indiqué une IP, une plage ou un CIDR, et que la valeur se trouve dans « Escopos de rede autorizados » (Périmètres réseau autorisés). Les noms d’hôte et les URL ne sont pas acceptés dans ce champ. Vérifiez aussi les exclusions et les limites d’hôtes. Ajustez les paramètres globaux lorsqu’aucun scan n’est en cours.

Dans quel fuseau horaire les heures sont-elles affichées ?

Dans le fuseau de votre navigateur, avec son abréviation à côté, par exemple « 02/11/2026, 14:21 BRT ». Le serveur enregistre chaque horaire avec son fuseau : une personne qui ouvre l’interface depuis un autre endroit voit donc l’heure correcte pour elle.

Aucun nouvel élément n’apparaît dans la comparaison

Vérifiez qu’il existe une référence antérieure compatible et que la comparaison a été activée. Utilisez les mêmes adresses IP et les mêmes options de couverture. Passez en revue les avertissements de couverture, l’allowlist et le filtre « Somente novos » (Nouveaux uniquement). Lors de la première exécution, il n’existe pas de baseline pour identifier les nouveautés.

Prêt pour le prochain scan ?

Choisissez la cible, vérifiez la politique et suivez l’évolution.
